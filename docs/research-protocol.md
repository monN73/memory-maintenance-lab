# research-protocol.md

规定核心研究问题（**不同的外部记忆维护方法会造成什么影响**）、实验单位、控制变量、预算契约与参考 Baseline 策略谱系。

## 研究规则

本项目旨在建立记忆维护研究的可复现、可归因**参考 Baseline 起点**：在严格控制上下文预算与固定历史回放的条件下，系统比较不同外部记忆维护范式（窗口淘汰、抽取/摘要压缩、无界/有界归档检索、只追加/可更新撤回结构化事实记忆及其变体）会造成什么影响，定位信息在写入、更新、撤回、压缩、淘汰与读取中的失效环节。

**阶段边界说明**：当前研究主线完全聚焦于 **`direct runner` 下的外部记忆维护方法比较（RQ1 与 RQ4）**；涉及 Agent 原生记忆机制与外部编排交互的测试（RQ2 与 RQ3，如 Hermes 接入）**明确暂缓**，以避免 Agent 专属系统提示词、工具定义开销与内部双层压缩混淆外部维护方法本身的因果效应。变更协议必须更新 protocol_version 与 config_id；已完成 run 使用当时冻结的配置，不追溯改写。

### 1. 四个问题与允许的结论

| 问题 | 当前状态 | 对照方式 | 能支持的结论 |
| --- | --- | --- | --- |
| **RQ1：不同的外部记忆维护方法如何影响记忆质量与资源消耗？** | **核心主线（已实施并持续扩展）** | 相同历史回放、相同 wrapper、相同 8K 回答输入预算、相同读取权限，仅改变外部维护策略或单组件（如归档容量、淘汰规则、更新/撤回动作、前端提取器） | 该外部维护方法或组件在给定预算与任务切片下的准确性、证据保留率与延迟/Token 成本；同时改变多组件只称方法包比较 |
| **RQ4：记忆在哪个维护环节、什么时候失效？** | **核心主线（已实施并持续扩展）** | 有时效标注的隔离探针（`on_maintenance` / `every_turn`）、Final Readout 共同检查点确定性/语义审计、维护前后快照与槽位占用统计 | 首次观测失败区间、失效环节归因（前端漏提 / 维护遗漏 / 容量淘汰 / 旧值残留 / 读出未命中 / 证据在但答错 / 执行中断） |
| RQ2：Agent 原生机制如何改变外部策略效果？ | **暂缓（远期扩展）** | 同 agent 内 external on/off × 一个 native mechanism on/off | 该原生机制下的条件增益与交互，不泛化为整个 agent 的因果效应 |
| RQ3：外部编排本身有什么影响？ | **暂缓（远期扩展）** | 同策略、native profile、输入与预算，更换编排；先比较 identity 控制 | 编排路径的开销/副作用；条件无法匹配时仅称系统比较 |

LongMemEval 最终成绩与维护 trace 是互补证据；只提高最终成绩不足以证明记忆没有损失。起步研究不追求所有组合，也不输出统一的“最佳 memory”排名。

### 2. 实验单位与身份

- 一个 run：一个数据实例 × 一个 experiment cell × 一次 repeat；内部包含全部历史 session、维护事件及最终问答。
- cell 固定 strategy_spec、agent/version、native_profile、orchestration_profile、预算、模型、session policy、history access 与评估协议。
- comparison 明确 treatment、control、changed_factors 和 hypothesis。单组件消融仅允许一个预注册因子改变；方法包可以多因子变化，但结论只能到包级。
- question_id 是配对统计单位；若多个问题共享同一历史，使用 history_group_id 聚类重采样，避免伪独立。重复运行、检查点与同题不同变体不当作独立题目。
- run_id 唯一；失败重试属于同 run 的 attempt，不新建“更成功”的独立重复。保留所有尝试与终止原因。

记录身份参考 [run-manifest.json](../templates/run-manifest.json)、[experiment-cells.json](../configs/experiment-cells.json)。配置是草案，null 必填值未补齐不能启动正式实验。

### 3. 三种比较必须分开

**算法比较**：固定摄入、预算执行器、输出槽位、调度、原始历史访问权与下游 reader；主要比较维护输出及同 reader 的最终问答。

**agent 内比较**：固定 agent 与编排路径，改变一个原生能力或外加策略。被禁用能力确实不可调用，需要配置/代码路径和针对性验证证据。

**系统比较**：保持相同数据任务，但保留各系统原生生命周期或工具。报告所有差异，可比较效用/成本，不把总差值归因于某个维护算法。

首批 N0–N4 属于基线方法包。当前 N3/N4 同时改变 representation、merge_update 和 compaction，即使输入与预算相同，也只能称 method_bundle 对照。若后续研究单独的压缩算子，需新增保持表示规范、更新规则和读取接口一致的策略；不能给现有结果追溯贴上单组件标签。

### 各方法的窗口与容量（direct runner）

这里的窗口指策略可以提供给回答模型的输入，不等同于模型总上下文容量。LongMemEval 回放原始历史，摄入阶段不调用回答模型，最终问题出现后再构造回答请求。所有 token 判断使用 `approx-utf8-v1` 估算；服务端实际 tokenizer、模型容量及输出用量需要单独核实。

| 方法 | 回放及最终回答时可用内容 | 容量与维护 |
| --- | --- | --- |
| N0 | 不保留历史；最终只提供系统提示和当前问题 | 默认输入检查 B=8192；回放时当前完整 exchange 也参与检查 |
| N1 / N5 | 全部已摄入历史和当前输入；N5 分块再按原序拼回 | 不按 B 裁剪；必须指定 `--n1-context-tokens`，输入估算上限为指定总容量减 512 输出预留；超过记 `overflow` |
| N2 | 最近保留的原始完整 exchange 和当前输入 | 默认 B=8192；超过触发阈值时淘汰旧轮次，不生成记忆 |
| N3 | 抽取式记忆 M、近期原始 exchange 和当前输入 | 与 N2 同样的触发和目标；维护时先预留 M（≤2048），再分配近期历史（≤4096） |
| N4 / N6 | LLM 摘要 M、近期原始 exchange 和当前输入 | 与 N3 使用相同外围预算分配；N4 增量摘要，N6 分块摘要再合并（N6 因辅助 API 消耗巨大暂不作常规批量运行） |
| N7 | BM25 从无界归档选出的原文 M、近期原始 exchange 和当前输入 | 默认 B=8192；M≤2048，近期历史维护时≤4096；归档池无容量硬上限 |
| N8 | BM25 从有界归档（先进先出淘汰）选出的原文 M、近期原始 exchange 和当前输入 | 与 N7 相同回答输入上限（B=8192，M≤2048），归档池设硬上限（默认 16384 tokens），满载时按先进先出（FIFO）淘汰最旧轮次 |
| N9 | 只追加规则事实记忆 M、近期原始 exchange 和当前输入 | 默认 B=8192，M≤2048；仅从 `user_text` 提取 `(entity, attr, value)` 追加并保留来源轮次，读出按实体/属性匹配 |
| N10 | 可更新/撤回规则事实记忆 M、近期原始 exchange 和当前输入 | 与 N9 共用提取器、容量（M≤2048）、近期窗口和读出规则；同 `(entity, attr)` 更新时覆盖旧值，撤回时写入占用同一 2K 预算的显式 `[RETRACTED]` 标记（再次声明可恢复） |
| N11 | BM25 从有界归档（精确去重后先进先出淘汰）选出的原文 M、近期原始 exchange 和当前输入 | 与 N8 共用同一归档容量上限（默认 16384 tokens）和 BM25 读出器；归档写入时对规范化重复原文保留最新轮次，满载后再按先进先出淘汰 |
| N12 | BM25 从有界归档（会话均衡淘汰）选出的原文 M、近期原始 exchange 和当前输入 | 与 N8、N11 共用同一归档容量上限和 BM25 读出器；归档满载时优先从当前归档占用最大的 session 中淘汰最旧轮次，防止单一长会话刷爆归档 |
| N13 | 结构化可更新/撤回事实优先 + BM25 原文兜底混合 M、近期原始 exchange 和当前输入 | 保持 B=8192、M≤2048；事实表仅存命中结构化规则的 `(entity, attr, value / [RETRACTED])`，读出时优先填入匹配事实，剩余 M 预算由 BM25 从原文归档中补充召回 |
| N14 | 增强前端提取 + 可更新/撤回事实记忆 M、近期原始 exchange 和当前输入 | 与 N10 共用同一后端状态槽位（M≤2048）与更新/撤回规则，仅升级前端提取器（扩展自然语言状态变更句式或轻量结构化抽取）以消融前端提取召回率瓶颈 |

对 N2–N4/N6/N7–N14，默认触发阈值为 floor(0.8 × 8192)=6553，**严格大于**才触发；维护目标 T=floor(0.6 × 8192)=4915。令 F 为系统提示和当前完整输入的估算大小：N2 维护时近期历史上限为 min(4096, T−F)；N3/N4/N7–N14 的 M 预留 m=min(2048, T−F)，近期历史上限为 min(4096, T−F−m)。当前 exchange 已计入 F，不计入该近期历史上限。完整轮次按最近优先选择；若最近的某一轮放不下，不跳过该轮继续选择更旧内容。

4096 和 2048 是**维护发生时的上限**，不是每一轮都限制近期内容或记忆占用；两次维护之间近期历史可以继续增长。F>T 且 F≤B 时清空旧记忆和近期历史并记录 `target_unreachable`；F>B 时记 `overflow`。N1 不保证正确率最高，其资源消耗通常与受限方法不同。不要将差异解释为等成本或 LLM 压缩的单组件因果效应。

CLI 的 `--budget` 只调整 B；近期历史上限 4096 和记忆上限 2048 当前为代码默认值，不能通过 CLI 直接设置。扩大 B 不会自动等比例扩大这两个上限，预算扫描时需单独说明。N4 的 `--n4-output-tokens` 是每次 API 生成上限，默认 4096，与 M 的估算预算不是同一数字或计量方式。实际参数以每次 manifest 的 `effective_budget` 为准；`configs/` 是设计记录，并不自动加载。


B=8192 是 N0/N2/N3/N4/N6/N7 的默认输入预算，不是“仅记忆正文预算”；N1 使用单独指定的模型总容量。主模型最大输出为 512，且实际模型窗口必须容纳输入和输出预留。固定开销、原生注入、外加 M、近期历史、问题与工具定义全部计入 B。

固定历史摄入阶段虽然不调用回答模型，也按相同序列化器计算候选上下文 token，避免只在最终问题到来时才维护；最终问题首次出现时再按实际长度校验，不能提前泄露问题文本。对受控 N2/N3/N4，候选请求 >0.8B 时触发维护，目标 ≤0.6B；M≤2048、近期历史≤4096 都是上限而非必须填满。令 T=floor(0.6B)，F 为固定开销与当前完整输入的序列化 token。若 F≤T，N3/N4 先预留 m=min(2048,T−F)，再从最近向前保留不超过 min(4096,T−F−m) 的完整轮次；m 是本次维护输出硬上限。原有 M 和移出的轮次一起进入维护器。最终再用实际序列化请求复核，消息包装和分隔符必须计入开销；不得用各片段 token 简单相加替代复核。N2 不预留 M，保留不超过 min(4096,T−F) 的最近完整轮次。F>T 时进入 target_unreachable 分支，只保留不可裁剪输入并逐项记录被淘汰状态；F>B 则终止。m=0 时不调用压缩模型，清空 M 并记录 budget_eviction；原始审计历史仍保存，但策略不可读取已淘汰且未授权恢复的原文。

预算执行器必须保存完整确定性算法和 hash。压缩结果超限时按冻结规则重试，仍超限记 maintenance_budget_error，禁止隐式截断成成功。单个不可分轮次或固定开销超过目标但未超过 B 时记 target_unreachable，并允许该轮≤B；超过 B 终止。不得无限压缩循环。受控策略共享执行器，原生系统采用其实际规则并单独标注。

当前 N4 不执行独立的 maintenance_input_limit；API 生成上限默认 4096，最多两次逻辑压缩尝试，分别记录返回的 usage。辅助模型能否接收全部待压缩内容须先验证，不默认其窗口足够。探针/评估调用也需明确预算，计入 evaluation_cost；不能给主方法的失败分支偷偷增加记忆预算。

只在最终可见预算相同时称等上下文预算；不称等总成本。另报全程输入/输出 token、实际计费 token、延迟、缓存与重试。首次实现无需做等总成本约束，但必须记录这些成本。

### 5. 溢出、缺失与交互的可解释性

N1 不压缩、不截断；8K 下读不完长历史属于容量失败。A（外加与原生维护都关闭）同样可能失效：四格端到端成功率能反映“是否能完成”，但不能因此证明记忆质量的协同。

先预选依据输入长度而非实验成败的短历史子集，验证四格均具备容量条件，再做质量交互；长历史压力组报告 overflow/完成率/端到端交互，并称 reliability interaction。不要只保留四格都成功的题后宣称无偏质量差异。四格有效样本覆盖不足则报告 not_identifiable，不强行给交互结论。

每个固定计划题集，报告：成功判对数/计划数、判对数/有效 judge 数、有效预测数/计划数、有效 judge 数/计划数。最后一个为 judge coverage，另可报有效 judge 数/有效预测数；分母写在列名中。judge 失败不是模型答错；成功/计划是保守的端到端成功指标，不冒充语义准确率。

overflow 是与遗忘不同的竞争终点，不视为普通的未失效右删失；正常观察结束才标 right_censored。中途 API 错误单列，不能默认删失与方法无关。未曾保留/答对与“先有后失”分开。单个检查点的正误变化是 observed_forgetting，不是遗忘机理的证明。

### 6. 开发、冻结与统计

30 题开发集可调参，不能反复用于挑最优后宣称泛化优势。Oracle 链路样本也属于开发暴露：与 S/M 中同 question_id 或同历史组的题一起标记。正式比较使用预先固定、未用于调参的题集；全量公开成绩另报开发重叠。

smoke 每组合 1 次；正式重复次数在开发方差和成本评估后冻结，初始建议 3 次，不保证足够统计功效。温度 0 不保证绝对确定。保存 provider/model fingerprint、采样 seed 支持情况、运行时间；按题随机化/交错策略执行顺序，避免时间漂移和缓存热度系统性偏向某策略。

预注册一个主要比较与主要指标，其他分题型/策略筛选结果标探索性。使用配对差值与 95% 聚类 bootstrap 区间（建议 2000 次，固定 seed），报告题数、分母和重复波动；小样本宽区间如实保留。若做多项显著性检验须预先声明校正方法，否则不输出“显著优于”。

judge 固定模型与 prompt。抽检预先随机选定的至少 10% 有效判定及全部争议样本；遮蔽策略名，记录判定依据和分歧。官方分数保持原样，人工复核列为独立标签。未知 API 模型漂移会限制严格复现，须披露。

### 7. 原生 memory 与外部编排的权责

strategy 决定维护内容；native_profile 决定 agent 自带机制；orchestration_profile 决定何时、通过何处、以什么权限触发二者。详见[agent-integration.md](agent-integration.md)。

同一输入的 identity 编排不应改写原文或读取隐藏历史；若带来包装、额外回答、工具调用或调度差异，必须记录。替换策略时其他条件不变；无法做到则标 wrapper_confounded，而非假定无影响。

agent 能力状态分 configured、effective、activation、observability 四项；supported/unsupported 归入可控性，不混为 on/off。读到磁盘记忆不代表当前 prompt 可见；没有事件不代表功能关闭。

### 8. 开跑前的最低验收

1. 锁定数据、ID 清单、协议/策略/编排/native profile、模型、judge 与代码版本。
2. 通过数据标签隔离、run 状态隔离、预算超限、探针不回写、原生机制启停和原文访问权限检查。
3. 每个方法的实际请求、维护前后状态、执行链与成本可追溯。
4. 校验实验单元与配对差异；不满足控制要求的组合自动标 blocked/observational。
5. 明确主比较、样本分组、错误处理与终止规则，再执行付费批次。

这些是本项目的研究质量要求，不代表已获某种外部认证。当前只能认定设计经过梳理，运行有效性仍须实现后验证。

## 起步实验与执行流程

本节按前文研究规则展开；外部编排与扩展见 [agent-integration.md](agent-integration.md)。

### 1. 范围与术语

- **历史 H**：完整原始对话，作为实验审计数据保存；不意味着策略可以读取全部历史。
- **工作上下文 C**：本次真正提交给模型的消息，包含系统指令、近期历史和已注入记忆。
- **显式记忆 M**：从历史维护出来的文本，可以是摘要、摘录、事实条目；可跨轮或跨会话保存。
- **Compaction**：缩短历史或记忆的操作，可以是截断、去重、抽取或 LLM 重写。
- **分割**：改变处理单元，本身不等于检索，也不等于信息丢失。全量重组和 top-k 选择必须分别实验。
- **无记忆**：必须说明是无历史，还是仅无显式 M。Long context 有历史信息，不应标成完全无记忆。

主要观察 maintenance：写入、合并、去重、修订、删除、预算淘汰与反复压缩。首轮不引入 embedding 检索，不优化底层架构。

### 2. 无 harness 实验矩阵

以下 N/H 编号仅为第一批实现预设，不限制后续方法。完整可组合策略空间和原生机制交互实验见[agent-integration.md](agent-integration.md)。

下表都由轻量 runner 直接构造模型请求。系统提示词、模型版本、输出预算、输入对话和采样设置保持一致。

| ID | 策略 | 模型可见的历史 | 显式 M | 维护方式 |
| --- | --- | --- | --- | --- |
| N0 | Current only | 当前输入 | 无 | 每轮清空历史，无历史对照（非数学下界） |
| N1 | Long context | 全部历史 | 无 | 不压缩；超预算记录 overflow 并停止该分支 |
| N2 | Sliding window | 最近完整轮次 | 无 | 从最旧轮次开始淘汰 |
| N3 | Extractive compaction | 最近完整轮次 + 摘录 | 有 | 确定性去重和句子抽取，无 LLM |
| N4 | LLM compaction | 最近完整轮次 + 摘要 | 有 | 增量压缩旧摘要和新移出的轮次 |
| N5 | Chunked full replay | 分块后按原序全量重组 | 无 | 不筛选，检查分割/边界影响 |
| N6 | Chunked LLM compaction | 近期历史 + 分块摘要 | 有 | 每块摘要再合并，与 N4 使用同等最终预算（因辅助 API 消耗过大暂缓常规批测） |
| N7 | BM25 retrieval memory | 最近完整轮次 + BM25 召回原文 | 有 | 移出窗口轮次建本地无界 BM25 索引；提问时召回 top-k 填入 M，无 LLM 维护 |
| N8 | Bounded archive BM25 (FIFO) | 最近完整轮次 + 有界归档 BM25 召回 | 有 | 沿用 N7 写入与读取，归档池设硬上限（默认 16K tokens），按先进先出淘汰最旧轮次 |
| N9 | Append-only fact memory | 最近完整轮次 + 只追加规则事实 | 有 | 仅从 `user_text` 提取事实条目，每次陈述追加并保留来源轮次，读出按实体/属性匹配 |
| N10 | Updatable fact memory | 最近完整轮次 + 可更新/撤回事实 | 有 | 与 N9 共用提取器、预算和读取规则；同实体属性更新时替换旧值，撤回时写入占用 2K 预算的显式 `[RETRACTED]` 标记 |
| N11 | Bounded archive BM25 (Dedup) | 最近完整轮次 + 去重有界归档 BM25 召回 | 有 | 与 N8 同归档容量上限（默认 16K tokens）和 BM25 读出；归档先精确去重保留最新原文，满载再按先进先出淘汰 |
| N12 | Bounded archive BM25 (Session-balanced) | 最近完整轮次 + 会话均衡有界归档 BM25 召回 | 有 | 与 N8、N11 同归档容量上限和 BM25 读出；满载时从归档占用最大的 session 中淘汰最旧轮次 |
| N13 | Fact + BM25 hybrid memory | 最近完整轮次 + 结构化事实优先 + BM25 原文兜底 | 有 | 事实表仅存结构化 `(entity, attr, value / [RETRACTED])`；读出时优先填入匹配事实，剩余 M 预算由 BM25 原文召回补充 |
| N14 | Enhanced-extractor updatable fact memory | 最近完整轮次 + 增强提取可更新/撤回事实 | 有 | 与 N10 共用同一后端状态槽位与更新/撤回语义，仅升级前端提取器以消融自然语言更新的提取召回率瓶颈 |

所有策略统一采用 `N + 数字`（`N0–N14`）一级编号，不使用带连字符的子编号：首批 N0–N4；第二批 N5/N7/N8/N9/N10；第三批补充对照为有界归档多淘汰规则（`N8` vs `N11` vs `N12`）与结构化事实前端提取/混合读取（`N10` vs `N13` vs `N14`）。N5 若重组后与 N1 请求完全一致，应作为实现一致性检查，而非独立有效策略。若加入分隔符，应单独标明格式变量。

N3 初版规则固定为：按消息内句界切句；标准化文本完全相同则保留最新来源；按来源时间从新到旧选取能放入预算的完整句，最终按时间顺序输出。保留来源 turn_id。它不具备语义修订能力，过时值冲突正是观察对象。不能读取 gold 标注来筛选句子。

N4 的增量输入仅限旧 M 和这次移出的历史，不允许每轮偷偷从完整 H 恢复信息。全量重摘要作为后续独立策略。N6 固定分块大小、重叠量、合并顺序，并记录每次辅助模型调用（因每次维护对各分块及合并均需调用 LLM，API 成本极高，目前保留代码实现，暂不执行全量运行）。

N7 使用与 N3/N4 相同的回答输入上限 `B=8192`、触发条件 `candidate > floor(0.8B)`（默认从 6554 起）、目标 `T=floor(0.6B)=4915`。摄入时将正常淘汰的完整轮次写入本地归档，未限制归档容量；摄入时不调用回答模型或使用最终问题。最终提问后，归档非空即进入检索分支，即使候选输入没有超过触发阈值；正常路径用已归档和本次移出的轮次做 BM25 排序，按预算填入 M（最多 `min(2048, T−F)`），按原顺序序列化。`search_latency_ms` 单独记录。归档容量与回答输入上限是两个变量；N7 是端到端存储加检索基线，不能与 N2–N4 的差值直接当作维护策略的效果。

#### 补充对照 1（方案 A）：有界归档同容量多淘汰规则对照（N8 vs N11 vs N12）

复用同一份 N7 的摄入历史、归档写入时点、近期窗口和最终 BM25 读取规则，将不同归档淘汰规则分别编码为独立的一级策略编号：**`N8`**（先进先出淘汰，已完成 `16K` 在线评测）、**`N11`**（精确去重保留最新原文后再按先进先出淘汰）、**`N12`**（会话均衡淘汰：从归档占用最大的会话中淘汰最旧轮次，防止单一长会话挤占全部归档）。`N8`、`N11`、`N12` 在每一档共享完全相同的归档容量（默认 16384 tokens，离线回放默认 8192），单位为逐条序列化后的估算 token 之和，包含来源标记但不计运行时索引内存，回答窗口和 M 不随之改变。仅在读出时使用问题；策略不读取评估标注。*(注：在 v1.0 Baseline 过程主结果收齐前，`N11`/`N12` 仅作扩编预留，不替代当前过程可比性补齐工作。)*

离线对照将「读前仍存储」与「进入最终输入」分开计算。标注单位、分母、缺失处理和产物见 [evaluation.md](evaluation.md#n7-离线回放存储与读取分开计算)。

#### 补充对照 2：结构化事实记忆的状态维护、混合读取与前端提取对照（N9 vs N10；N13/N14 扩展对照）

1. **后端状态维护对照（`N9` vs `N10`，已完成）**：
   - `N9`（只追加）与 `N10`（可更新 + 显式 `[RETRACTED]` 撤回）100% 共用提取器（仅提取 `user_text`）、`M≤2048` 容量、近期窗口与检索排序，唯一变量为维护动作。
   - 在早期自建可控场景调试验证（已归档至 `archive/dev-scenarios/`）中已确认：`N10` 后端更新/撤回与防误删逻辑本身有效，而随后全面转回冻结的 LongMemEval 真实更新切片（`s-ku-10`）则揭示：真实对话中 `99.25%` 的用户句未命中固定更新正则而退化为 `fallback`，说明**真实开放对话的瓶颈在于前端事实提取召回率与兜底挤占，而非后端更新/撤回机制**。现行及后续实验全面采用 LongMemEval 等公开基准，不再使用自建合成数据集。
2. **混合读取与增强前端提取补充策略（`N13` 与 `N14`，方案 A 扩展）**：
   - **`N13`（结构化事实优先 + BM25 原文兜底混合记忆，与 `N10` 构成 `method_bundle` 对照）**：冻结规则包括——① 事实表仅存命中结构化规则的 `(entity, attr, value / [RETRACTED])`（不再把未命中对话作为 `context | s_...` 塞入 `2K` 事实表）；② 原文归档采用与 `N8` 一致的 `16384` tokens FIFO 硬上限（`--n8-archive-tokens 16384`）；③ 读出时结构化事实优先占用 `M≤2048`，剩余 `M` 预算由 BM25 从归档白名单中补充召回；④ BM25 候选排除已在结构化事实表命中的 `turn_id`（`fact_tids`），避免同一轮次双占 `M` 槽位。由于 `N13` 相对 `N10` 同时改变了写入过滤、外部归档可用性与混合读出规则，其对照严格记为 **`method_bundle`**，不宣称单组件因果。
   - **`N14`（增强前端提取器 + 可更新/撤回状态槽位，与 `N10` 构成单组件对照）**：保持 `N10` 后端更新与 `[RETRACTED]` 撤回逻辑及 `M≤2048` 完全不变，仅升级前端提取器（扩展自然语言进度/计数与状态变更句式），直接与 `N10` 对照以量化前端提取召回率提升带来的真实更新收益。
   - **开发暴露声明**：`s-ku-10` 中的 `01493427` 与 `45dc21b6` 两条题目曾用于检查真实对话通路并暴露 `N14` 提取规则与 `P3` 快照重放验收；在后续统计与泛化解释中，这两题明确标记为公开切片内的**开发暴露样本**。

### 4. 数据设计：公开基准为主

主评测改为 LongMemEval S cleaned，Oracle 做链路诊断，M 做后续压力测试；版本、字段映射、历史回放与防泄漏要求见[evaluation.md](evaluation.md)。公开基准完整摄入后回答最终问题；逐轮诊断只用于有合适前缀标注的子集。

以下人工数据保留作辅助机制诊断，不承担主要效果结论。

每条场景由固定消息、时间标注、事实生命周期和探针组成。推荐先人工写 6 类各 1 条、每条 40 轮，之后扩展到每类 5 条、每条 80–200 轮；长短由实际 token 预算决定，不能只依赖轮数。

| 场景 | 构造方法 | 要观察的失效 |
| --- | --- | --- |
| 远距离事实 | 早期给出随机项目码，插入无关文本后提问 | 旧信息丢失 |
| 事实修订 | 日期/负责人先后变更，含同名不同项目 | 旧值覆盖新值、实体串扰 |
| 删除与撤回 | 明确撤销一项要求，之后追问 | 被删除信息再次进入活跃记忆 |
| 多主题交错 | A/B/C 项目轮流出现并重复近似表述 | 合并错误、冗余挤占预算 |
| 精确字符串 | 路径、数字、否定条件、随机 ID | 摘要改写导致细节损失 |
| 跨会话延续 | 同一 run 内开启新 session 后询问 | 持久记忆未写入或未加载 |

每个事实包含 fact_id、entity、value、introduced_at、valid_from、valid_to、supersedes、source_turn_ids；有效区间为 `[valid_from, valid_to)`，null 表示仍有效。删除后的事实不计入当前保留率分母，但需要测泄漏/复活。

探针分为当前状态查询、历史状态查询、跨事实组合、应当不知道。历史查询明确时间，避免把正确历史答案误判为过时值。标注文件独立存放，模型与压缩器不能读取。

### 5. 预算与控制变量

动态预算分配、辅助调用窗口和 target_unreachable 处理遵循前文“预算执行契约”；下列 M 与近期历史数值均为上限，不是容量预留之和。

N0/N2/N3/N4/N6/N7 默认输入预算 B=8192 tokens、最大输出 512 tokens；N1/N5 使用独立的模型容量限制；这是实验默认值，不是对任何模型能力的声明。总输入包含系统指令、工具定义、M、历史与当前消息，模型还需有足够输出窗口。

- N3/N4：M 上限 2048，近期历史目标上限 4096；剩余空间容纳系统指令与当前输入。按实际请求总 token 再校验，不能简单把各上限相加当成合规。
- 触发：请求预估输入大于 0.8B 时维护；维护后目标不高于 0.6B，且必须不超过 B。若单条当前消息或固定开销已经过大，记录 budget_error。
- N2 按同一触发/目标处理，使用完整轮次裁剪；N1 不触发维护，按单独指定的模型总容量减去回答预留检查，超过该输入容量记录 overflow。N1 与 8K 组不是等预算比较。
- 首轮使用模型对应 tokenizer，记录版本与特殊消息开销；无法获得精确值时标记 estimate，另存 provider usage。不要用中文字符数冒充 token 数。
- 主要对照固定最终可见预算；辅助调用数量、总 token、成本和延迟单独记录。后续再做等总成本对照。
- 固定回答模型、压缩模型、prompt hash、温度、seed（若支持）、工具集与 runner 版本；不支持 seed 必须记录。smoke 每组合 1 次；正式重复次数在开发阶段估计方差后冻结，起步建议 3 次。

### 6. 每轮执行协议

以下是自建交互场景流程。LongMemEval 使用固定 user+assistant 消息摄入，不重新生成历史回答；按[evaluation.md](evaluation.md)执行 benchmark_final 和 maintenance_trace。

1. 加载本轮固定消息和当前状态，保存维护前快照；上一轮的真实回答已进入历史。
2. 计算候选请求，按策略触发维护，保存所有事件及维护后快照。
3. 保存实际提交的完整消息、顺序和 hash；调用回答模型并记录 usage、耗时与错误。
4. 追加本轮回答，执行策略规定的轮末持久写入，分别保存“用于本次回答的状态”和“供下轮使用的状态”。
5. 从供下轮使用的状态复制评估分支，按冻结的 readout_mode 发送探针：snapshot_readout 禁止继续维护/恢复，operational_probe 照常执行并记录。两种模式分别报告，问题、回答和副作用均不写回主轨迹。
6. 用标注评估快照与探针答案，输出一行 turn 日志及各 probe 记录。评估调用费用与主运行分开。

使用固定用户消息回放，避免前一轮答错后改变后续问题。不同策略生成的 assistant 消息仍会使历史不同：这是端到端轨迹实验。LongMemEval 主协议已经采用固定 user+assistant 全轨迹回放，专门隔离维护算法的损失。

压缩调用失败、输出超预算等均记事件。允许的重试次数预先固定；不得默默切换策略。无可用状态则结束该 run 并标明基础设施失败。

### 7. 开展顺序与验收

先用附带 6 轮场景验证修订和日志，再构造足够长的干扰输入，在专门构造的长样例中让 N3/N4 各至少实际触发 3 次维护。每轮都跑固定事实探针；较大实验可降频，但必须报告失效区间。

主线先做 Oracle 5 题链路检查，再做 S 固定分层 30 题 × 5 策略 × 1 次 = 150 run；参数冻结后扩大全量。原有 6 场景 × 5 策略 × 3 次 = 90 run 降为可选人工诊断批次。探针和 judge 调用另计。

验收：实际请求可还原；每个压缩事件有前后快照；能在结果页定位某事实第一次消失、第一次答错、第一次使用旧值；报告同时保留未失效、overflow 和运行错误，不能只展示成功样本。

### 复核后的解释边界

相同 0.8B 触发阈值不保证相同维护轮次：策略输出长度不同，会改变后续触发时机。这是策略自适应运行的总效果。若要隔离单次维护损失，另做固定输入快照、固定输出预算的局部对照；若要比较递归漂移，可按独立于各策略输出的累计摄入 token 安排共同维护时点。不同调度条件新建 comparison，不从自适应结果直接推断算子优劣。

输入长度预选的四格质量子集还需有预设的触发机会：例如在共同的较低阈值启用维护，但四格总历史仍不超过硬窗口。先用独立 smoke 样例验证启用路径实际触发；若正式题未触发，只报告该配置的零暴露条件，不按触发后的结果挑题。四格足够完整但原生机制始终未激活，也不能认定其没有效果。

研究起点允许将 30 题视为开发筛选；不能保证此规模足以稳定区分相近方法。正式样本量与重复次数需依据开发方差、可接受的差值区间宽度及费用冻结。更复杂的方法扩展应晚于第一批可解释结果。

## 第一版 Baseline 的双主结果与跨策略过程可比性规则

### 1. 两份互补主结果（Baseline v1.0 交付边界）

以“为后续研究建立外部记忆维护 baseline”为目标，现有策略覆盖（`N0–N5`、`N7–N10`）与两层数据集（可控场景 + LongMemEval 切片）已足以作为第一版基线；现阶段不急于扩编更多策略编号或接入 Hermes，而应确保第一版 Baseline 具备以下**两份互补的主结果**：

1. **主结果一：相同任务上的最终问答成绩、完成率与资源成本**：
   - 呈现 `oracle-5`、`s-dev-30` 与 `s-ku-10`（其中 `s-ku-10-clean` 已覆盖同批完整的 `N7–N10`，`s-ku-10-merged5` 经配置/版本核验并入补跑后的 `N4` 构成五策略对比；`N6` 因高成本暂缓、其余 `N0–N3/N5` 尚未进入 `s-ku-10` 同批）的端到端成功率、条件准确率、错误分布、三段式延迟与 Token 成本。
2. **主结果二：同一事实在不同维护方法下的生命周期配对追踪**：
   - 围绕 **“同一事实经过不同策略后何时写入、更新、保留或丢失”**，形成跨策略可配对的逐证据维护轨迹，弥补纯 `final_only` 批次无法比较全部方法首次丢失区间的缺口。

### 2. 逐事实过程追踪的四个关键记录与三类状态区分

对每条被追踪事实（优先基于可控场景的 gold 生命周期与代表性真实前缀构建），必须在轨迹汇总中显式记录 4 件事：
1. **写入记录**：事实是否在初次出现并移出近期窗口后成功写入 `M` 或归档；
2. **预期修订记录**：哪次显式更新或撤回应当发生，实际维护动作是否命中同一 `(entity, attr)`；
3. **共同检查点状态**：在相同历史前缀的共同检查点上，`M` / 可见上下文中该事实的状态、值与邻近键是否正确；
4. **同探针读出结果**：同一隔离探针在该共同检查点上能否读出并答对对应时效的期望值。

在此基础上，必须严格区分**三类结果**，禁止混为一谈：
- **漏写（`acquisition_omission`）**：信息从未被正确写入 `M` 或归档；
- **遗忘（`valid_fact_forgetting`）**：曾正确写入、在目标检查点仍属有效事实、随后从 `M` 或可读状态中消失（如因压缩丢失或旧值撑爆容量触发淘汰）；
- **正确维护（`intended_revision_removal`）**：按更新或撤回指令删除、覆盖或失效化不再有效的旧值。只有将三者分开，才能准确判定诸如 `N10` 删除旧值或写入 `[RETRACTED]` 究竟是收益还是误删损失。

### 3. 共同历史前缀对齐与区间报告规范

- **事件序号不可直接跨策略对齐**：例如在相同自适应触发阈值下，`N9` 与 `N10`（或 `N4` 与 `N7`）的第 $k$ 次维护事件往往发生在不同的对话 `turn_id`。各自 `events.jsonl` 适合单策略内部归因（解释某次动作改变了什么），而跨策略配对比较**必须对齐到相同的对话 `turn_id` 或 session 末共同检查点**。
- **离散检查点只报告失效区间**：若仅观测到“上一次共同检查点正确、下一次共同检查点错误”，统一报告首次失效区间 `(last_ok_turn, first_fail_turn]`，禁止将探针首错轮次直接写成精确遗忘轮次。

## Implementation revision

当前主问题是不同维护方法相对完整历史的效果损失和资源节省。N1 使用显式声明的模型容量，N2–N4 使用维护预算；二者不作为等资源对照。N3/N4 对齐外围预算和触发规则，但自适应触发轮次可能不同，结果解释为方法整体差异。N4 不引入隐式回退。具体已实施规则以 [evaluation.md](evaluation.md) 的 N1 / N4 implementation revision 为准；此前涉及 N1 统一 8K 限制的描述仅适用于旧开发批次。

已有调试题作为开发集，冻结配置后使用未参与调参的样本验证。旧记录不删除、不改写，不混入新版正式比较。

### 方案 A 的实现与验收边界
