# roadmap.md

记录项目审查结论、当前参考 Baseline 建设状态及后续实施顺序。

## 项目审查

### 总体判断

研究方向聚焦于 **“不同的外部记忆维护方法会造成什么影响”**。以“为后续研究建立外部记忆维护 baseline”为目标，目前框架（`direct runner` + 8K 预算执行器 + 隔离探针 + 审计管线）及已覆盖的核心范式（`N0–N5`、`N7–N10`）**已足以作为第一版基线**；但以“系统地说明不同维护方法在哪一轮、因为什么操作导致信息丢失”为目标，还缺少**跨策略对齐的逐事实维护过程配对主结果**。

v1.0 的两份交付物为任务成绩与成本表、逐证据维护轨迹。正式切片采用公开 LongMemEval，历史人工场景仅作归档案例。

### 发现与处置

| 发现 | 影响 | 本轮处置 |
| --- | --- | --- |
| 编排缺少独立身份与 identity 控制 | 包装 prompt、hook 和调度可能被误归为算法收益 | 新增 orchestration profile 与比较契约；现阶段暂缓 Agent 接入以消除包装混淆 |
| A 格关闭压缩后可能全部 overflow | 四格差值主要是容量效应 | 区分质量与 reliability 交互；`N1/N5` 独立使用 `--n1-context-tokens 131072` |
| M/近期上限相加超过压缩目标，辅助模型预算未定义 | 实现产生不同隐式裁剪 | 明确上限/动态分配、不可达目标和辅助调用预算 |
| 多维方法包与单组件消融混用 | 无法归因具体方法 | `N0–N4/N7` 作为范式方法包对照；`N7 vs N8`、`N8 vs N11 vs N12`（同容量淘汰规则）、`N9 vs N10`（只追加 vs 更新/撤回）、`N10 vs N13 vs N14` 作为严密单变量对照 |
| 注册表不包含计划运行的 N0–N4 | 配置无法解析 | 补齐基线，新增显式 cell manifest；候选方法保留 proposed |
| 1/3/5 次重复口径不一致 | 数量与统计解释混乱 | smoke/开发筛选 1 次，正式预先冻结；3 次仅起步建议 |
| 长历史最终答错与精确遗忘混用 | 得出没有观测支持的失效时点 | 区分 acquisition、observed forgetting、overflow 与 execution_failure |
| probe 可再次触发维护 | “维护前”状态可能在测量时被改变 | 探针在只读状态快照上隔离执行，不回写主历史 |
| N9/N10 早期同时抽取助手文本且正则在闲聊上空转 | 助手建议误触发撤回、99.88% 兜底句撑爆 2K 槽位 | 修正为仅提取 `user_text`、冻结 `[RETRACTED]` 显式失效语义、修复同源 `false_additions` 审计，并通过可控场景 + `s-ku-10` 分层验证 |
| run 身份遗漏 profile/cell；一个轮次可有多个维护事件 | 结果碰撞、重叠率难解释 | run manifest、事件级指标（含 `fact_memory_stats`）、明确全局轮次映射 |
| Oracle 开发题可能与 S 测试重叠 | 开发暴露导致偏差 | 统一按问题/历史组标记开发暴露；`s-ku-10` 按与提取器无关的等距规则提前冻结 |
| 仅按题独立重采样 | 同历史多问题造成伪独立 | 支持 history_group_id 聚类与配对 bootstrap CI |

Hermes 审计在 P0 即开始，完整 agent 批次在 direct 日志成熟后开展，避免先实现大量不受支持的实验。起步不要求所有候选方法、所有四格或新数据库。

最小实现边界：dataset loader → strategy + budget executor → direct/agent adapter + orchestration → evaluator → reporter。简单 Python 模块和 JSONL 足够，不预先搭插件平台。接口责任见[agent-integration.md](agent-integration.md)。

关键验证包括：数据顺序/角色不变、gold 隔离、run 隔离、probe 分支不回写、预算错误不隐式降级、原文不可越权回读、禁用机制不触发、最终请求可追溯。静态校验不能代替这些运行验证。

后续候选优先考虑：增量/全量摘要的原文访问差异、固定预算下分块、结构化时间版本记忆、重要性淘汰、原生持久写入/历史恢复、相同策略不同编排。发现交互后再做组件消融；按结果选中的新假设须在新题集验证。

每阶段产出一个 reference bundle：冻结配置和清单、原始预测/事件/快照、评分器版本、统计报告、代表失败案例、限制与下一轮假设。此 bundle 是后续发展参考，而非一张忽略条件的总排名。

## 最终设计复核

当前结构适合作为起点，进入正式评测前仍需锁定模型、数据和 adapter 能力。此次复核修正了 N3/N4 单组件归因错误，改为表示/合并/压缩共同变化的方法包；明确预算预留顺序与零预算处理，区分自然调度和固定时点诊断，并补充探针超窗规则。

同时修复文档合并时链接替换误吞的事实有效期说明与预算章节标题。静态校验扩展为检查文件名链接、锚点、声明的策略差异与批次数量；检查通过仍不等于实验运行有效。

优先执行 N2/N3/N4 的可追溯小样例，N0/N1 提供边界参照；随后用 Hermes smoke 审计真实触发与编排影响。第一批结果出来前，不继续扩大方法矩阵或增加基础设施。

## N1 / N4 follow-up

1. 已实现：N1 独立模型容量参数、N4 保守目标与草稿缩短重试、manifest 有效配置记录；通过离线模拟验证，尚未在线验证。
2. 开发验证：核实服务容量，验证完整 exchange 预算检查的边界与在线行为，使用独立开发样本校准 N4 长度控制；记录失败，不因分数较低临时修改方法。
3. 冻结协议：固定模型、回答提示、预算、维护提示、重试规则、数据清单及评分器。统一重跑 N0–N4，旧批次作为开发归档。
4. 过程分析：标注相关证据，比较维护前后遗漏、错误新增和旧值残留；文本重叠率仅作辅助。
5. 扩展：预算与触发规则扫描、相同输入的配对压缩实验，再进行 Hermes 原生记忆与外部维护组合实验。
